# 前端界面文案走词条表，Rust 侧直接改字面量

本 fork 要把用户界面改成中文，但仍打算长期从 `upstream`（drmowinckels/entracte）
合并上游更新。前端为此引入一个词条表：调用点写 `t("key")`，语言是模块级状态，
**默认 `en`，只在应用启动时切到 `zh-CN`**；Rust 侧则不做任何抽象，直接把约 30 处
托盘/通知文案和约 116 条默认内容硬替换成中文。这个不对称是刻意的。

## 为什么前端要词条表

前端有 79 个测试文件、11202 行，其中约 328 处断言直接写死英文文案
（`getByText("Active hours")` 这类）。硬替换会逼我们改掉全部 328 处，从此每次
`git merge upstream/main` 在测试文件上都是大面积冲突 —— 等于把上游最有价值的一块
资产变成永久冲突区。

让 `t()` 默认返回英文、只有应用启动时才切中文，测试就拿到英文，**328 处断言一个字
都不用改**，测试文件与上游保持逐字节一致。这是选词条表的唯一理由，也是全部理由。

## 为什么 Rust 侧反而不做

Rust 侧受影响的测试断言是个位数，UI 文案只有约 30 处。搭一套语言状态 + 字典 +
完备性测试的开销，远超它能保护的东西。为对称而对称就是过度设计。

## 后果

- 中文渲染路径不被现有测试覆盖。补一个字典完备性测试（每个 `en` 键都有 `zh-CN`
  对应、无空值、占位符数量一致）作为替代保障；该测试是新文件，不与上游冲突。
- 上游新增的文案在词条表里缺 key 时**回落英文**而不是报错。界面不会崩，只是那块暂时
  是英文 —— 这是期望行为，不是 bug。
- 前后端语言机制不一致，读代码的人会觉得奇怪。本 ADR 就是为了回答那个「为什么」。

## 关于枚举值的红线

`src-tauri/src/scheduler/settings.rs` 与 `src/views/settings/types.ts` 之间有一组
parity 测试（`settings.rs:2539` 起，以及 `src/views/settings/parity.test.ts`），
断言 Rust 枚举与 TS 联合类型的**取值**一致。`"overlay"` / `"windowed"` /
`"notification"` 这类是**落盘值**，永远不翻译；只翻译它们对应的 label。parity 测试
是这条红线的自动守卫。
